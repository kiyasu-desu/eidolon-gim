# 源码发布检查

发布源码、配置示例、处理工具、合成测试和维护文档。角色模型、贴图、动作、剧情原文／译文、向量、用户库、录音、凭据及本机报告不随源码发布。

`release-policy.json` 列出源码根目录、根文件、大小上限和逐文件固定 SHA 的界面资源。二进制仅保留列明的字体、图标、通用礼物插画和通话提示音等资源；新增或修改时须显式复核清单。模型、数据库等禁止路径不能通过清单豁免。

`.scratch/`、`coordination/`、`corpus/`、调研截图和运行产物留在本机。历史上已跟踪的文件必须从 Git 索引移出；忽略规则不会将它们移除。上游许可、第三方署名及必要的历史 ADR 保留。

## 检查实际提交

暂存期望源码后在根目录执行：

```sh
python scripts/check-release.py
git diff --cached --check
git diff --cached --stat
```

默认检查 Git 索引中的 blob，能识别被暂存的敏感文件，不读取忽略的本机资源。提交后和 CI 使用：

```sh
python scripts/check-release.py --ref HEAD
python scripts/check-gim-scope.py
python -m unittest discover -s scripts/tests -v
```

检查拒绝私有目录、模型／数据库／归档、未批准的二进制、越界符号链接、模型／剧情／向量 JSON 载荷和常见凭据格式。输出只含路径、行号和原因，不输出匹配值。规则不能保证识别任意秘密或剧情文本，仍需人工复核文件清单和新增正文。

`--report <本机报告路径>` 可保存只含元数据的 JSON。报告留在忽略目录，不提交原始扫描内容。

## 分支与 CI

`main` 是源码交付基线。PR、`main`、`codex/gim-release` 和 `v*` 标签按 `.github/workflows/ci.yml` 触发检查；发布检查分支只测试和构建，不推镜像。`main` 与版本标签在检查全部通过后推送本项目命名空间的 GHCR 镜像。CI 不自动切换生产服务。

## 统一本地、GitHub 与生产

一次交付使用一个完整提交SHA，核对代码、角色配置、部署文件及镜像的来源。部署者先完成本地检查并取得本次发布授权，再按以下顺序操作：

1. 确认工作区干净、私有资源仍未被跟踪；获取远端最新状态，核对合入关系，用普通提交／快进保留历史。
2. 推送约定的交付提交，等待该SHA的CI全部成功。以完整SHA核对结果，避免把较早版本的绿灯当作新版本验证。
3. 使用该提交构建的前后端镜像，核对 `org.opencontainers.image.revision`；优先固定镜像摘要，记录对应仓库、提交和角色／部署文件SHA。不要把旧镜像仅换标签就当作新版本构建。
4. 切换前保存应用配置、用户库和独立剧情库的一致性备份，记录现有容器及私有资源清单。生产保留自己的环境变量、数据卷和凭据。
5. 仅切换本项目服务；执行健康、匿名访问、角色资源、配置与用户数据完整性核对。涉及实际运行行为的改动按部署说明补充文字／通话验收。
6. 确认本地HEAD、远端main、生产发布清单及两份镜像revision对应同一提交。保存镜像摘要和回退位置；应用回退与数据库恢复分别处理。

具体提交、服务器地址、镜像摘要和私有验收结果保存在各环境的发布记录中，不把凭据、用户数据或内部报告提交到GitHub。[下一阶段](project-roadmap.md)的目标不构成本次发布之外的实施授权。

普通推送保留 Git 历史。当前文件树的移除不等于历史擦除；本流程不重写历史，不清除上游或此前提交中的文件。
